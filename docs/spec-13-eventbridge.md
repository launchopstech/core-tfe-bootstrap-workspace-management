# Spec-13: EventBridge Event Routing

**Status:** `[ ] not started`
**Phase:** Wave 2 — Event Mesh
**Default depends on:** `iam`, `spec-04-ai-queue` (SQS queues as event targets), `spec-10-ai-obs` (CloudWatch alarm targets)
**Blocks:** HITL interruption wiring (spec-14 realtime needs events to push), full agent observability fan-out
**Repo(s):** core-tfe-bootstrap-workspace-management

---

## Business Rule

System-level events generated by agent execution (task complete, approval required, failure)
must be routable to multiple independent consumers without tight coupling between producers
and consumers.

---

## Goal

Provision an EventBridge custom event bus and rule set for routing agent lifecycle events
to the correct downstream consumers. This is the **event fan-out layer** — separate from SQS
(which handles task queuing and backpressure).

---

## Context

### EventBridge vs SQS — Boundary Clarification

These two services solve different problems and are complementary, not redundant:

| | SQS (spec-04) | EventBridge (this spec) |
|---|---|---|
| Pattern | Task queuing | Event routing |
| Consumers | One worker per message | Multiple independent consumers |
| Delivery | At-least-once, backpressure support | At-least-once, rule-based routing |
| Use case | "Process this task" | "Something happened — notify all interested parties" |
| HITL | HITL approval queue (ordered, FIFO) | HITL notification trigger (fan-out to WebSocket + SNS) |

**Rule**: Use SQS when a task needs to be processed by exactly one worker. Use EventBridge
when an event needs to notify multiple, independent consumers simultaneously.

### Agent Lifecycle Events

```
agent.task.submitted     → worker picks up from SQS (not EventBridge)
agent.task.started       → EventBridge: update state ledger listener + observability
agent.step.completed     → EventBridge: audit log, observability
agent.tool.invoked       → EventBridge: blast radius control audit
agent.approval.required  → EventBridge: WebSocket push (spec-14) + SNS alert
agent.task.completed     → EventBridge: notification service + observability + billing trigger
agent.task.failed        → EventBridge: DLQ alert + SNS + retry decision
agent.session.timeout    → EventBridge: cleanup trigger + state archival
```

### HITL Interruption Flow

```
Reasoning loop encounters high-risk tool
  → Writes AWAITING_APPROVAL to DynamoDB state ledger (spec-03)
  → Publishes agent.approval.required to EventBridge
  → Pauses execution, waits on SQS HITL FIFO queue

EventBridge routes agent.approval.required to:
  ├── spec-14 WebSocket: push state update to connected client UI
  └── SNS topic: email/Slack notification to approver

Approver acts in UI
  → API writes approval/rejection to SQS HITL FIFO queue
  → Reasoning loop receives approval and resumes
```

## `accounts.tf.json` Contract

### Input Configuration (stable)

```json
"eventbridge": {
  "eventbridge_config_json": {
    "bus_name_suffix": "ai-events",
    "rules": {
      "approval-required": {
        "enabled": true,
        "pattern": { "detail-type": ["agent.approval.required"] },
        "targets": ["sns-hitl-alerts", "websocket-push"]
      },
      "task-completed": {
        "enabled": true,
        "pattern": { "detail-type": ["agent.task.completed"] },
        "targets": ["sns-ops", "cloudwatch-metrics"]
      },
      "task-failed": {
        "enabled": true,
        "pattern": { "detail-type": ["agent.task.failed"] },
        "targets": ["sns-ops", "dlq-alert"]
      },
      "audit-all": {
        "enabled": true,
        "pattern": { "source": ["agent-forge"] },
        "targets": ["cloudwatch-logs"]
      }
    },
    "retention_days": 90,
    "schema_registry": true
  }
}
```

### Implementation Notes (current)

- Custom event bus named `<client_id>-<env>-ai-events` (not the default bus — isolation per client)
- EventBridge Schema Registry enabled to document event shapes and generate SDK bindings
- `targets` reference logical names mapped to actual ARNs at apply time (SNS topics from variable set, WebSocket API from spec-14 output, CloudWatch log groups from spec-10)
- Archive enabled for `retention_days` — replay capability for debugging stuck agent sessions

## Terraform Resources Created

- `aws_cloudwatch_event_bus` — custom event bus (one per client environment)
- `aws_cloudwatch_event_rule` — one per enabled rule in config
- `aws_cloudwatch_event_target` — targets per rule (SNS, CloudWatch Logs, Lambda)
- `aws_cloudwatch_event_archive` — event archive for replay
- `aws_schemas_registry` — EventBridge Schema Registry
- `aws_iam_policy` — PutEvents permission for reasoning Lambda/ECS task role

---

## Validation Checklist

- [ ] **Decoupling**: Event producer (forge-core-ai) only calls `PutEvents` — it does not know or care which consumers are subscribed. Adding a new consumer does not require producer code change.
- [ ] **HITL flow**: `agent.approval.required` event reliably reaches WebSocket layer (spec-14) within 1 second of being published. Verified with EventBridge event replay.
- [ ] **Audit completeness**: All events with `source: agent-forge` land in CloudWatch Logs archive. No event type is silently dropped.
- [ ] **Fan-out scalability**: Event bus can deliver to all targets simultaneously without dropping events during concurrent agent session spikes.

---

## Tradeoffs

| Concern | Decision | Rationale |
|---------|----------|-----------|
| Custom bus vs default bus | Custom per client | Default bus receives all AWS service events; mixing agent events creates noise and security surface |
| EventBridge vs SNS for fan-out | EventBridge | Content-based routing (filter by event type) without upstream knowing who subscribes |
| Schema Registry | Enabled | Prevents event shape drift between producer and consumers; generates type-safe SDK bindings |
| Archive retention | 90 days | Match checkpoints TTL in spec-03 — allows replay for debugging any session within retention window |
